Verification States · 验证状态含义

T/F/U 三值验证器的安全含义

理解 Valid、Insufficient、Invalid 在云数据库暴露路径侦测场景下的实际意义。

Valid · 已确认暴露

含义：路径上所有 6 个维度的证据均已收集且支持该路径成立。

安全影响：

  • 攻击者可以沿此路径访问高敏数据
  • 需要立即修复（关闭公网访问、撤销权限、加密数据）
  • 在审计报告中应标记为"已确认风险"

示例：公网 IP → 安全组放行 3306 端口 → IAM 角色有 SELECT 权限 → 表包含身份证字段 → 审计日志显示已访问 → 时间线连贯

Insufficient · 证据不足

含义：路径上至少一个维度的证据缺失（Unknown），但无反证。

安全影响：

  • 无法确定路径是否可被利用
  • 需要进一步调查（补充缺失证据）
  • 在审计报告中应标记为"待验证风险"
  • 可能是由于监控覆盖不全或日志缺失

示例：公网 IP → 安全组放行 3306 端口 → [权限证据缺失] → 表包含身份证字段

Invalid · 已确认不可达

含义：路径上至少一个维度的证据明确反驳该路径（Contradicted）。

安全影响：

  • 攻击者无法沿此路径访问数据
  • 无需立即修复，但应记录为"已排除风险"
  • 可作为安全加固的有效性证明
  • 帮助识别哪些控制措施有效阻止了攻击

示例：公网 IP → [安全组拒绝 3306 端口] → 后续路径不再检查

为什么三值比二值更好？
传统的二值判断（可达/不可达）无法区分"证据不足"和"已确认不可达"。在云安全审计中，这两者需要不同的处理策略：
  • Insufficient → 需要补充监控、收集更多证据
  • Invalid → 可以归档为"已排除风险"，并记录哪些控制措施生效
这种区分帮助安全团队更高效地分配调查资源，避免在已确认安全的路径上浪费时间。

Technical Summary · 技术说明

这一天完成了哪些技术工作

本页重点说明已有 Demo 如何被拆解为数据、证据语义、路径搜索、实验脚本和可视化几个可检查的技术模块。

解决了什么问题？

传统方法的缺陷：现有的云数据库暴露路径侦测方法（如 DFS + GateScore）存在三个根本问题：

  • 无法区分反证与缺证：将"证据不足"和"已确认不可达"混为一谈，导致误报率高
  • 只依赖网络可达性：过度关注 entry/reach 维度，忽略权限、敏感数据、审计等其他关键证据
  • 缺乏部分可见性处理：无法在证据不完整的情况下做出合理判断

我们的解决方案：

  • C1 异构云证据语义化：引入 6 维证据边（status/source/time/confidence/query_cost/raw_evidence），显式标记每条证据的状态和来源
  • C2 反证感知路径搜索：RefuteAwareBeamSearch 在搜索阶段即考虑证据状态，优先探索高价值路径，主动剪枝反证路径
  • T/F/U 三值验证器：区分 Valid（已确认暴露）、Insufficient（证据不足）、Invalid（已确认不可达），提供更精细的安全判断
这些指标说明了什么？
dataset_v1 test R@3 = 0.6462

在按 group_id 切分后的 test split 上，RefuteAwareBeamSearch 的 R@3 高于 Full-constrained DFS + GateScore（0.2000）。hard_test 上 R@3=0.6000，高于对应基线 0.2200。

FPR = 0.0000（当前 split 记录）

dev/validation/test/hard_test 中样本级 FPR 仍记录为 0。这个数字只能说明当前构造语料和规则下没有出现 false positive，不能外推为真实云环境零误报。

T/F/U 语义一致性 = 672/672

当前 672 条路径标签均与验证器输出一致。这个指标用于检查语义化规则与标签体系是否一致，不应写成真实云环境泛化准确率。

308 样本 · 672 路径标签

dataset_v1 将 104 个 group 切成 dev/validation/test/hard_test，确保同源 base 与变体不跨 split。SDDP 当前仍作为案例切片，不进入主实验 ground truth。

当前局限性与改进方向
  • 语料是构造的，非真实生产数据：308 样本来自 pathbench_60、cloudgoat 和 samples_v2；SDDP 当前作为案例切片单独展示。在真实云环境中的泛化能力待验证。
    → 改进方向：接入真实脱敏数据（从 DMS/POP/SLS 导出实际 SDDP 数据）
  • 缺乏消融实验：无法确定 RefuteAwareBeamSearch 的哪个组件贡献最大（temporal 维度？query_cost？beam 剪枝？）。
    → 改进方向：逐个移除组件，对比 R@3、FPR、时间复杂度
  • 未与真实云安全工具对比：只与 DFS 变体对比，缺乏与 PMapper、Cartography、AWS Security Hub 等工具的对比。
    → 改进方向：在相同样本上运行真实工具，对比召回率和误报率
  • C3 仅预留接口：验证反馈驱动的安全调查模型训练未实际展开。
    → 改进方向：基于 corpus 生成 SFT/DPO 训练样本，训练实际模型
